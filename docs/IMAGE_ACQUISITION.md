# 공고 이미지를 어떻게 확보하는가

파이프라인 전체가 **"공고 이미지 한 장"**에서 시작하는데, 그 한 장을 어디서 어떻게
가져오는지가 설계에 없었다. 이 문서가 그 구멍을 메운다.

---

## 1. 사람인 API는 이미지를 주지 않는다

`https://oapi.saramin.co.kr/job-search`의 응답 필드 전부다.

```
jobs
 └ job
    id · url · active
    posting-timestamp · posting-date · modification-timestamp
    expiration-timestamp · expiration-date
    company (기업명, 기업정보페이지 링크)
    position (제목, 지역, 근무형태, 업종, 직무)
    experience-level · required-education-level
    keyword · salary · read-cnt · apply-cnt
```

**본문 상세 내용 필드가 없다. 이미지 URL 필드도 없다.**

`url`은 *"채용공고 표준 URL"* — 사람인 공고 **페이지 링크**다. 이미지가 아니다.

> 이건 이 API가 잘못 만들어진 게 아니다. **채용정보 검색·집계용 API**이지 공고 본문
> 배포용이 아니다. 애초에 그 용도로 설계되지 않았다.

### 그래서 과제 요구와 충돌한다

과제는 두 가지를 동시에 요구한다.

> ① 사람인 공고를 **API로 크롤링**해서 확보한다
> ② **공고 내용이 이미지인 공고**를 고른다

**API만으로는 ②를 만족할 수 없다.** ①과 ②를 동시에 하려면 API 밖의 단계가 반드시 들어간다.
이걸 숨기지 않고 설계에 드러낸다.

---

## 2. 데모 경로 — 실제로는 네 단계다

지금까지 "API로 크롤링"이라고 한 줄로 적었던 것을 풀면 이렇다.

| | 하는 일 | API인가 | 법적 노출 |
|---|---|---|---|
| **1** | `job-search` 호출 → 공고 목록 + `url` | ✅ **API** | 이용약관 범위 안 |
| **2** | 그 `url`의 **HTML 페이지를 받는다** | ❌ 스크래핑 | **약관 범위 밖** |
| **3** | HTML에서 본문 `<img>` 태그를 찾는다 | ❌ 파싱 | **약관 범위 밖** |
| **4** | 사람인 CDN에서 **이미지 파일을 내려받는다** | ❌ 다운로드 | **가장 노출됨** |

**1번만 API다.** 2~4번은 전부 API 밖이다.

### 왜 2~4가 약관 범위 밖인가

사람인 오픈 API 주의사항의 문구다.

> *"사람인 채용정보를 **제공하는 범위 내에서** API 서비스를 사용할 수 있는 **제한된 권리**를
> 취득합니다."*

**부여된 권리가 "API가 제공하는 범위"로 한정된다.** 그런데 API는 이미지를 제공하지 않는다.
따라서 **이미지 취득은 그 권리에 애초에 포함되지 않는다.** 금지 조항을 어기는 문제가
아니라, **허락받은 적이 없는 행위**다.

여기에 별개로 걸리는 것들:

- **저작권** — 공고 이미지는 그 자체로 저작물이다(도안·편집). 복제·전송에 권리자 허락이 필요하다
- **DB제작자의 권리**(저작권법 §93) — 상당한 투자로 구축한 DB의 소재를 반복 복제하면 침해 소지
- **CDN 무단 이용** — 이미지 파일을 우리 서버로 내려받는 것은 사람인 인프라 사용이다

> 주의사항에 **크롤링·스크래핑 금지 조항이 명시적으로 있지는 않았다.** 하지만 "명시적
> 금지가 없다"가 "허락됐다"는 뜻이 아니다. 위의 "제한된 권리" 문구가 이미 범위를 닫고 있다.

### 그래서 데모에서는 어떻게 하나

**한다. 하되 숨기지 않는다.** 과제가 요구한 경로이고, 데모 목적이며, 우리가 제출하는 것은
목업 이력서에 대한 채점 결과이지 사람인 데이터의 재배포가 아니다.

지키는 선:

- 공고 **2개만** 가져온다. 대량 수집을 하지 않는다
- 이미지는 `data/postings/`에 두고 **레포에 커밋하지 않는다** (`.gitignore`)
- **공고 본문 텍스트를 저장하지 않는다.** 이미지에서 파싱한 구조화 조건만 남긴다
- 사람인 **공고 ID·URL을 결과 JSON에 남기지 않는다** — 남기면 우리 DB가 사람인 DB의
  부분 복제가 된다
- 코드에 **`SaraminSource`는 데모 전용**이라고 박고, 결과에 `source_kind`를 실어 UI가
  「데모 데이터」 배지를 띄운다

## 3. 프로덕션 경로 — 고객사는 API를 쓰지 않는다

**이게 이번에 놓쳤던 핵심이다.**

`docs/LEGAL_ARCHITECTURE.md`에서 "고객사가 자사 공고를 보낸다"고만 썼는데, **고객사가
무엇을 어떻게 보내는지**가 비어 있었다. 그래서 마치 고객사가 사람인 API를 대신 호출하는
것처럼 읽혔다.

**아니다. 고객사는 사람인 API가 필요 없다.**

```
공고 이미지를 누가 만들었나?  →  고객사 (디자인·인사팀)
그 원본 파일은 어디 있나?     →  고객사 시스템
사람인에는 어떻게 올라갔나?   →  고객사가 업로드했다
```

**원본은 처음부터 고객사에 있다.** 사람인은 그걸 받아 게시한 곳이다.
그래서 프로덕션 경로는 사람인을 **아예 거치지 않는다.**

| | 데모 | 프로덕션 |
|---|---|---|
| 이미지 출처 | 사람인 CDN | **고객사 원본 에셋** |
| 취득 방법 | API + 페이지 스크래핑 + 다운로드 | 고객사가 **업로드(push)** |
| 사람인 관여 | 있음 | **없음** |
| 권리 근거 | 없음 (허락받은 적 없음) | 고객사의 **권리 보증 조항** |
| 우리 호출 | 있음 (pull) | **없음** |

> 화살표를 뒤집는다는 말의 진짜 의미가 이것이다. 단순히 방향만 바꾸는 게 아니라,
> **사람인이라는 중간 노드가 경로에서 사라진다.**

## 3.5. API는 빠지지 않는다 — 역할이 바뀐다

여기서 모순처럼 보이는 게 생긴다.

> 과제는 **"API로 크롤링해서 확보"**를 요구하는데, 프로덕션 경로에서는 사람인이 사라진다.
> **그러면 API가 플로우에 필요 없다는 뜻인가?** 그럴 거면 과제가 왜 API를 쓰라고 했나?

모순이 아니다. **내가 API를 "본문을 나르는 파이프"로만 봤기 때문에 생긴 착시**다.
본문이 고객사에서 오면 파이프가 할 일이 없어지는 게 당연하다.

그런데 **API가 실제로 잘하는 것은 본문이 아니다.** 응답 필드를 다시 보자.

```
id · url · active · posting-date · modification-timestamp · expiration-date
company · position · experience-level · required-education-level · keyword · salary
```

**전부 메타데이터와 상태다.** 본문이 없는 게 이 API의 결함이 아니라 **성격**이다.

> **API는 본문을 나르는 파이프가 아니라, 고객사가 보낸 것을 검증하는 대조군이다.**

그렇게 보면 프로덕션 플로우에 **세 자리**가 생긴다.

### 역할 ① 동일성 확인 — 권리 보증의 기술적 뒷받침

고객사가 "이건 우리 공고다"라며 이미지를 보낸다. 그 말이 맞는지 우리는 어떻게 아는가?

`docs/LEGAL_ARCHITECTURE.md` §6-1에 **"고객사가 남의 공고를 보내면 우리는 모른다"**를
한계로 적어뒀다. **API가 그 한계를 메운다.**

```
고객사가 보낸 것       API로 조회한 것
company: "OO테크"  ↔  company (기업명)
title:   "백엔드..." ↔  position.title
게시일               ↔  posting-date
```

대응하는 공고가 실제로 게시돼 있으면 권리 보증 조항이 **말뿐이 아니게 된다.**

**한계**: 그 회사에 그런 제목의 공고가 있다는 것까지만 확인한다. **보낸 이미지가 그
공고의 이미지인지는 확인하지 못한다.** 부분적 방어다.

### 역할 ② 상태·수정 감시 — 승인을 무효화한다

**이게 가장 큰 자리다.** `active` · `expiration-date` · `modification-timestamp`가 있다.

| 상황 | API가 알려주는 것 | 우리가 하는 일 |
|---|---|---|
| 공고가 마감됨 | `active=0`, `expiration-date` 지남 | **채점 차단.** 마감된 공고로 랭킹을 돌리지 않는다 |
| 공고가 **수정됨** | `modification-timestamp`가 바뀜 | **승인 무효화 → 재승인 요구** |

두 번째가 결정적이다. Kairen OS의 규칙이 이렇다.

> `human_validated`는 사람이 **현재 revision**을 확인한 뒤에만 쓴다.

우리 승인 게이트는 **특정 시점의 공고**에 대한 것이다. 공고가 수정되면 그 승인은
**낡은 것**이 되는데, 지금 설계에는 그걸 알 방법이 없었다. 고객사가 알려주기 전까지는
낡은 루브릭으로 계속 채점한다.

그래서 `RubricProposal`에 공고 revision을 저장한다.

```python
class RubricProposal(BaseModel):
    ...
    posting_revision: str | None      # API의 modification-timestamp
    approved_at: datetime | None
```

`score()`가 실행 시점에 API로 현재 값을 조회해 다르면 **`ApprovalStale`을 던진다.**
검산 **G7**이 이걸 강제한다.

### 역할 ③ 파싱 교차검증 — 독립 출처

지금 설계의 가장 큰 약점이 **"파싱 품질에 시스템 전체가 인질로 잡힌다"**였다.
루브릭을 공고에서 생성하므로 파싱이 틀리면 루브릭 전체가 틀린다.

그런데 지금 파싱 검증 수단은 OCR 대조뿐인데, **OCR도 같은 이미지에서 나온다.**
같은 원본이 틀렸으면 둘 다 틀린다.

**API는 완전히 다른 출처다.**

| API 필드 | 대조할 파싱 결과 |
|---|---|
| `experience-level` | 이미지에서 읽은 경력 요구 |
| `required-education-level` | 이미지에서 읽은 학력 요구 |
| `position` (근무형태·업종·직무) | 이미지에서 읽은 직무 |

어긋나면 **파싱 결과의 신뢰도를 낮추고 승인 화면에 표시**한다. 자동으로 고치지 않는다 —
어느 쪽이 맞는지 우리가 정할 수 없다. **고객사가 정한다.**

**한계**: API가 주는 건 코드값 몇 개다. 요구조건 목록 전체를 검증하지 못한다.
**몇 개 필드만 대조하는 부분 검증**이다.

### 정리하면

<!-- 표 -->

| | 데모 | 프로덕션 |
|---|---|---|
| 공고 **본문·이미지** | API + 스크래핑 (**API 밖**) | **고객사 push** |
| 공고 **메타데이터** | API | **API** |
| 공고 **상태·수정 감시** | API | **API** |
| **파싱 교차검증** | API | **API** |

**API는 두 경로에 다 남는다.** 데모에서는 본문 취득까지 억지로 시켰고(그래서 3단계가
약관 밖), 프로덕션에서는 **원래 잘하는 일만** 시킨다.

그리고 이 용법은 **전부 약관 범위 안**이다 — 검색 API를 검색·메타데이터 용도로 쓰는 것이니까.
범위를 벗어났던 건 이미지 취득뿐이었다.

### 고객사에 원본이 없으면

현실적으로 있을 수 있다 — 외주 디자인, 담당자 퇴사, 파일 분실.

그때의 대체 경로: **고객사가 자기 공고 페이지에서 직접 내려받아 보낸다.**

법적으로 다르다 — **자기 저작물을 자기가 내려받는 것**이라 제3자 무단 복제가 아니다.
다만 **자동화되지 않는다.** 사람이 한 번 손을 대야 한다. 그게 이 경로의 비용이다.

**이 대체 경로를 우리가 자동화하면 안 된다.** 우리가 대신 내려받는 순간 데모 경로와
똑같아진다.

## 4. 놓치면 안 되는 것 — 두 이미지는 같은 파일이 아니다

데모와 프로덕션이 방향만 다른 게 아니다. **받는 이미지 자체가 다르다.**

| | 데모 (사람인 CDN) | 프로덕션 (고객사 원본) |
|---|---|---|
| 해상도 | 게시용으로 **리사이즈된 사본** | 원본 |
| 압축 | 웹 배포용 재압축 | 원본 |
| 분할 | 긴 공고는 **여러 장으로 잘려 있을 수 있음** | 원본 구성 |

이게 파이프라인 세 곳에 영향을 준다.

### ① 파싱 정확도

해상도가 낮으면 작은 글씨(우대사항·비고)를 못 읽는다. **하필 그 부분이 필수/우대 판정에
쓰인다.** 데모에서 잘 되던 파싱이 프로덕션에서 더 잘 될 수는 있어도, 반대는 아니다.

### ② bbox 좌표의 호환성 — 가장 중요하다

검산 **G4**가 모든 조건에 이미지 좌표를 요구하고, UI가 그 좌표로 공고 이미지에 네모를
그린다. 그런데 **좌표는 그 이미지 파일 기준**이다.

> 데모 이미지가 900px 폭이고 원본이 1800px이면, 데모에서 저장한 `bbox(120,340,880,392)`는
> 원본 위에서 **엉뚱한 자리**를 가리킨다.

그래서 `BBox`에 **기준 이미지의 크기를 같이 저장한다.**

```python
class BBox(BaseModel):
    page: int
    x1: int; y1: int; x2: int; y2: int
    img_w: int      # 이 좌표가 기준으로 삼은 이미지 폭
    img_h: int      #                        높이
```

UI는 `표시크기 / img_w`로 스케일한다. 이걸 안 하면 **데모에서 만든 결과를 프로덕션
이미지로 다시 보는 순간 근거 추적이 전부 어긋난다.**

### ③ 토큰 비용

OpenAI 비전은 이미지를 타일로 나눠 과금한다. 해상도가 2배면 타일 수가 늘어 **호출 비용이
오른다.** 데모에서 잰 비용을 프로덕션 예산으로 쓰면 안 된다.

## 5. 코드에 어떻게 남기나

```python
class PostingSource(Protocol):
    def list_postings(self, **q) -> list[PostingRef]: ...
    def fetch_images(self, posting_id: str) -> list[Path]: ...

class SaraminSource:
    """데모 전용. 프로덕션 금지.

    fetch_images()는 API가 아니다 — API로 얻은 url의 HTML을 받아
    본문 <img>를 찾아 CDN에서 내려받는다. 이 세 단계는 사람인 오픈 API가
    부여한 "제공하는 범위 내" 권리에 포함되지 않는다.
    docs/IMAGE_ACQUISITION.md §2 참조.
    """

class LocalSource:
    """개발·테스트. 이미 확보한 이미지를 읽는다. 네트워크 없음."""

class ClientFeedSource:
    """프로덕션. 고객사가 원본 에셋을 push한다. 사람인을 거치지 않는다.
    이번 과제에서는 구현하지 않는다. docs/IMAGE_ACQUISITION.md §3 참조.
    """
```

**`SaraminSource`에서 `list_postings()`와 `fetch_images()`를 메서드 두 개로 나눠 둔 것이
설계의 요점이다.** 앞의 것만 API고 뒤의 것은 아니다. 한 메서드로 합치면 그 차이가
코드에서 사라진다.

## 6. 정직하게 남는 것

1. **API만으로 이미지 공고를 확보할 수 없다는 것이 과제 요구의 구멍이다.** 우리는
   API + 스크래핑으로 해결했고, 그 사실을 숨기지 않는다
2. **사람인 약관에 스크래핑 금지 조항이 명시적으로 있는지 확인하지 못했다.** 주의사항
   페이지에는 없었지만 서비스 이용약관 전문은 확인하지 않았다
3. **프로덕션 경로를 구현하지 않았으므로 검증되지 않았다.** 고객사가 실제로 원본을
   갖고 있는 비율도 모른다
4. **법률 자문을 받지 않았다.** 설계 문서지 법적 판단이 아니다
