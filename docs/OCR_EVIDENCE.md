# OCR 실측 — 임계값 3개의 출처

`phases/matching-engine/step3.md`가 쓰는 임계값은 전부 여기서 나왔다. **읽히는 대로 정한
값이지 관례나 평판으로 고른 값이 아니다.** 실험 코드는 `spike/ocr_check/`에 있다.

측정 대상: 사람인 이미지 공고 1건 (한국어, 세로로 긴 단일 이미지, 불릿 목록형).
측정 시각: 2026-09-01 00:10~01:00 KST.

## 1. 엔진 선정 — EasyOCR을 뺀 이유

| 엔진 | 평균 신뢰도 | 소요 | 결과 |
|---|---|---|---|
| EasyOCR | **0.396** | ~15초 | **탈락** |
| EasyOCR (2배 확대) | 0.382 | ~40초 | 더 나빠졌다 |
| EasyOCR (3배 확대) | 0.396 | ~90초 | 그대로 |
| **PaddleOCR** (`lang="korean"`) | **0.936** | ~40초 (첫 회 모델 다운로드 별도) | **채택 — 기본** |
| **macOS Vision** (`.accurate`) | 0.802 | **~3초** | **채택 — 맥 개발용** |

**확대로 안 고쳐진 것이 결론을 갈랐다.** 2배·3배로 키워도 0.382 / 0.396이면 **해상도가
아니라 모델 문제**다. 「전처리를 더 해보자」로 시간을 태울 자리가 아니었다.
EasyOCR 출력은 한국어 단어가 형태를 유지하지 못하는 수준이었다.

Vision은 신뢰도 숫자가 Paddle보다 낮은데 **실제 텍스트는 거의 완벽했고 띄어쓰기가 살아
있었다.** 두 엔진의 `conf`가 같은 척도가 아니라는 뜻이므로, **신뢰도만으로 엔진을 고르면
안 된다.** 텍스트를 직접 봐야 한다.

**기본값을 Paddle로 둔 것은 정확도가 아니라 이식성 때문이다.** 평가자가 윈도우를 쓸 수
있고, Vision은 macOS에서만 돈다. Vision은 `--ocr-engine vision`으로 켠다.

> ⚠️ **PaddleOCR을 기본 설정 그대로 쓰면 맥이 멈춘다.** 2026-09-01 00:50에 실제로 멈췄다.
> 전 코어를 쓴다. `cpu_threads=2` + `OMP_NUM_THREADS`/`MKL_NUM_THREADS`/`OPENBLAS_NUM_THREADS=2`를
> **paddle import 전에** 걸어야 한다. 나중에 걸면 안 먹는다.

**PP-StructureV3(표 인식)는 로컬에서 안 돌린다.** 의존성(`paddlex[ocr]`) 설치 후 실행하면
모델 10여 개를 내려받고, 그 과정에서 맥이 다시 멈췄다. 표 문제는 다른 방법으로 푼다
(`step3.md` 3-B′ — 직무 행의 y 구간만 자른다).

## 2. 틀렸던 규칙 — 글자 크기로 헤더를 가른다

**확정된 규칙인 줄 알았고, 실측에서 틀렸다.**

| 측정 | 값 |
|---|---|
| 전체 줄 수 | 63 |
| 줄 높이 범위 | **12 ~ 14 px** |
| 헤더의 높이 | 12 ~ 14 px (본문과 **같다**) |

헤더는 크기가 아니라 **굵기와 색**으로 구분돼 있었다. 그리고 **OCR은 굵기도 색도 주지
않는다.** 그래서 이 신호는 존재하지 않는 것과 같다.

`step3.md`의 판정 사다리 5단계(시각 강조 → 등급 `E0`)가 **현재 경로에서 영원히 발동하지
않는 이유가 이것이다.** 자리는 남겼지만 `emphasized`는 항상 `False`이고,
그 사실을 `ParseReport.emphasis_available = False`로 결과에 적는다.
**「구현했는데 안 쓴다」가 아니라 「입력이 없다」**이고, 둘은 다르다.

## 3. 남은 신호 — x 들여쓰기

높이가 죽었으므로 **기하 신호는 x0 하나만 남았다.** 그건 살아 있었다.

x0 분포가 **4개 띠**로 갈렸고, 띠 사이에 **빈 구간**이 있었다.

```
x0:  38 ~ 60      ← 띠 1. 섹션 헤더
     [ 65~70px 빈 구간 — 여기 줄이 하나도 없다 ]
    125 ~ 140     ← 띠 2. 불릿 항목
    150 ~ 165     ← 띠 3. 이어지는 줄 / 하위 항목
    200+          ← 띠 4. 표 오른쪽 열
```

**`header_x_threshold = 100`은 그 빈 구간의 한가운데다.** 60과 125 사이 어디를 잡아도
같은 결과가 나온다 — 그래서 이 값은 **임의 상수가 아니다.** 읽어낸 값이다.

`continuation_tolerance = 4`(px)는 띠 2와 띠 3의 간격(~15px)보다 훨씬 작게 잡은 것이다.
「직전 항목보다 **조금이라도** 더 들여썼으면 이어지는 줄」이라는 규칙이고,
OCR 좌표의 흔들림(±2px)보다 크게만 두면 된다.

## 4. 두 엔진이 같은 구조를 냈다 — 이게 유일한 교차 검증이다

PaddleOCR과 macOS Vision은 **서로 다른 회사가 만든 서로 다른 모델**이다.
같은 이미지에서 두 엔진이 **거의 같은 bbox**를 냈고, **같은 4개 띠**를 만들었으며,
**같은 자리에 65~70px 빈 구간**이 생겼다.

**한 엔진에서만 확인된 임계값은 그 엔진의 특성일 수 있다.** 두 엔진이 독립적으로 같은
구조를 만들었다는 것이, 이 임계값이 이미지의 실제 레이아웃을 반영한다는 유일한 근거다.

## 5. 이 실측이 틀리는 조건 — 반드시 읽어라

**이 문서의 근거는 공고 1건이다.** 그 사실을 흐리지 않는다.

| 조건 | 무슨 일이 나나 | 어떻게 아나 |
|---|---|---|
| 다른 공고가 다른 들여쓰기 체계를 쓴다 | `header_x_threshold=100`이 헤더를 놓치거나 본문을 헤더로 본다 | `ParseReport.role_counts`의 `header`가 0이거나 비정상적으로 많다 |
| 다단 레이아웃 | 오른쪽 단이 「깊게 들여쓴 줄」로 읽혀 앞 항목에 병합된다 | `merged_continuations`가 항목 수보다 많다 |
| 헤더가 가운데 정렬 | x0가 커져 `item`으로 오분류된다 | `header`가 0인데 `item`이 많다 |
| 표 (KT 공고) | 셀 소속이 사라진다 | — **알려진 문제.** `step3.md` 3-B′로 대응 |
| 어두운 배경 + 장식 (넥슨 공고) | 신뢰도가 떨어진다 | `avg_conf`가 0.8 미만 |

**그래서 `ParseReport`를 UI 하단에 그대로 노출한다.** 임계값이 실측에서 나온 값이라
다른 공고에서 빗나갈 수 있고, 그때 **`role_counts`만 보면 어디가 틀어졌는지 보인다.**
숫자를 숨기고 「잘 동작합니다」라고 쓰는 것보다 이게 정직하다.

**`ambiguous`가 전체의 50%를 넘으면 이 규칙 체계가 그 공고에 안 맞는 것이다.**
그때는 조용히 진행하지 않고 예외를 던진다 (`step3.md` 3-E).

```bash
python -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m uvicorn app:app --port 8010

```

화면에서 조절할 수 있는 것: 엔진(paddle/vision) · `badgeX`(=`header_x_threshold`) ·
`contTol`(=`continuation_tolerance`). **슬라이더를 움직이면 분류가 실시간으로 바뀌므로,
위 §3의 「빈 구간」이 실재하는지 직접 확인할 수 있다.**

이 스파이크는 **확인용이고 제출물이 아니다.** 검증이 끝난 규칙만 `src/matching/parser/`로
옮긴다.
