# 고객사 경유 데이터 구조 (설계만, 구현 안 함)

과제 요구:

> **(구현 불필요) 법적 우회 구조 설계** — 채용 정보를 크롤링해서 저희(서비스 제공사)가
> 직접 적재하는 것은 법적으로 문제가 될 수 있습니다. 데이터가 저희가 아니라 **고객사를
> 거쳐서** 들어오는 구조를 설계해주세요. 실제로 구현하지 않으셔도 되고, README에
> 아키텍처로 정리해주시면 됩니다.

이 문서는 **README「법적 아키텍처」의 원재료**다. 법률 자문이 아니라 설계 문서다.

---

## 1. 무엇이 문제인가

과제 데모에서 우리가 하는 일은 이렇다.

```
사람인 서버 ──(API 크롤링)──▶ 우리 서버에 적재 ──▶ 파싱 ──▶ 채점
```

여기서 걸리는 것이 넷이다. **성격이 서로 다르다.**

| | 무엇 | 상대방 | 성격 |
|---|---|---|---|
| **A** | 공고 DB를 긁어 우리 DB에 쌓음 | 사람인 | **DB제작자의 권리**(저작권법 §93) 침해 소지 |
| **B** | 사람인이 투자해 모은 성과를 무단 사용 | 사람인 | **부정경쟁방지법** 성과 도용 소지 |
| **C** | API 이용약관의 목적 외 사용·재배포 | 사람인 | **계약 위반** |
| **D** | 이력서를 우리가 직접 수집·보관 | **지원자 개인** | **개인정보보호법** |

**D가 A~C보다 크다.** A~C는 사업자 사이의 문제라 계약으로 정리할 여지가 있지만, D는
정보주체가 제3자다. 그런데 과제 문면은 A~C만 말하고 있다.

> **판단**: 우리가 설계할 구조는 **A~C만이 아니라 D까지 같이 푸는 것**이어야 한다.
> 다행히 **같은 구조 하나가 둘 다 푼다.** 그게 이 문서의 결론이다.

## 2. 핵심 착상 — 화살표의 방향을 뒤집는다

공고의 **원래 권리자는 사람인이 아니라 그 공고를 낸 회사**다. 사람인은 그걸 모아 놓은
플랫폼이다.

그래서 이렇게 바꾼다.

```
[지금 — 데모]
  사람인 ──(우리가 긁는다)──▶ 우리

[설계 — 프로덕션]
  고객사 ──(고객사가 보낸다)──▶ 우리
     │
     └─ 자기 공고 · 자기가 받은 이력서 · 자기 채용 기준
```

**같은 데이터가 흐르는데 법적 성격이 달라진다.** 우리가 가져오면 무단 수집이고,
고객사가 보내면 **자기 데이터를 처리해달라고 맡기는 것**이다.

> [!example] 왜 이게 말장난이 아닌가
> 공고 원문의 저작권과 그 공고에 지원한 이력서의 관리 권한은 **원래부터 고객사에 있다.**
> 사람인은 게시 플랫폼이고, 우리는 채점 도구다. 지금 구조가 이상한 이유는
> **권리자를 건너뛰고 플랫폼에서 긁기 때문**이다. 방향을 뒤집는 건 우회가 아니라
> **원래 자리로 되돌리는 것**이다.

## 3. 설계 — 4개의 경계

```
┌─ 고객사(채용사) 영역 ────────────────────────────────┐
│                                                     │
│   자사 공고 이미지        지원자 이력서                │
│         │                     │                     │
│         └──────┬──────────────┘                     │
│                ▼                                     │
│        ① 고객사 커넥터 (고객사가 설치·실행)             │
│           · 권리 보증 서명                             │
│           · 개인정보 처리위탁 계약 체결                  │
└────────────────┼────────────────────────────────────┘
                 │  ② 좁은 통로 (push only)
                 ▼
┌─ 우리(수탁 처리자) 영역 ──────────────────────────────┐
│        ③ 수신 · 파싱 · 채점                            │
│           · 원본 미적재                                │
│           · 처리 후 즉시 파기                           │
│                ▼                                     │
│        ④ 결과 반환 → 고객사만 조회                      │
└─────────────────────────────────────────────────────┘
```

> **먼저 읽을 것**: 공고 이미지를 실제로 어떻게 확보하는지는 `docs/IMAGE_ACQUISITION.md`에
> 따로 있다. **사람인 API는 이미지를 주지 않는다** — 응답에 본문 필드도 이미지 URL 필드도
> 없다. 그래서 데모 경로는 API 1단계 + **API 밖 3단계**(페이지 스크래핑 → `<img>` 파싱 →
> CDN 다운로드)로 이뤄진다. 아래 ①이 그 3단계를 없애는 구조다.

### ① 고객사 커넥터 — 데이터를 **우리가 안 가져온다**

**고객사는 사람인 API를 쓰지 않는다.** 이 문서 초판에서 "고객사가 자사 공고를 보낸다"고만
써서, 마치 고객사가 API를 대신 호출하는 것처럼 읽혔다. 아니다.

```
공고 이미지를 누가 만들었나?  →  고객사 (디자인·인사팀)
그 원본 파일은 어디 있나?     →  고객사 시스템
사람인에는 어떻게 올라갔나?   →  고객사가 업로드했다
```

**원본은 처음부터 고객사에 있다.** 사람인은 그걸 받아 게시한 곳일 뿐이다.
그래서 프로덕션 경로에서는 **사람인이라는 중간 노드가 경로에서 통째로 사라진다.**
화살표를 뒤집는다는 말의 진짜 의미가 이것이다.

고객사 쪽에서 도는 컴포넌트다. 우리 서버가 사람인이나 고객사 시스템을 **호출하지 않는다.**
호출 방향이 항상 고객사 → 우리다(push).

**왜 push여야 하나**: pull이면 우리가 접근 권한을 갖게 되고, 접근 권한을 가진 순간
"무엇을 언제 얼마나 가져올지"를 우리가 정하게 된다. 그러면 다시 수집 주체가 된다.
push면 **범위를 고객사가 정한다.**

계약으로 붙는 것 둘:

- **권리 보증 조항** — 고객사가 "보내는 공고·이력서에 대해 처리 권한이 있으며, 제3자
  권리를 침해하지 않는다"고 보증한다. 위반 시 책임 귀속을 명시한다
- **개인정보 처리위탁 계약**(개인정보보호법 §26) — 이력서 때문에 필수다.
  이걸 맺으면 우리는 **수탁 처리자**가 되고, 위탁받은 목적 외 이용이 금지된다.
  **동의 주체는 고객사가 채용 과정에서 이미 받은 지원자 동의**다

### ② 좁은 통로 — 보내는 것을 최소화한다

| 보낸다 | 안 보낸다 |
|---|---|
| 공고 **이미지** (또는 파싱된 조건) | 사람인 공고 ID · 사람인 URL |
| 이력서 **본문 텍스트** | 지원자 이름 · 연락처 · 사진 · 주민번호 |
| 고객사가 정한 채용 기준 | 사람인 DB의 다른 공고 |

**사람인에서 온 식별자를 아예 받지 않는다.** 받으면 우리 DB가 사람인 DB의 부분 복제가
되어 §A(DB제작자의 권리)가 살아난다. 우리가 받는 건 **고객사가 자기 것이라고 보증한
그 공고 하나**뿐이다.

지원자 식별정보는 애초에 안 받는다 — **파이프라인에 마스킹 단계가 있는 이유가 이것**이다
(`src/matching/scorer/mask.py`). 마스킹이 블라인드 채용 대응이면서 동시에 개인정보
최소수집이다.

### ③ 원본 미적재 — 우리 DB에 남는 것

```
남긴다:  Requirement[] (구조화된 조건)  ·  Criterion[] (루브릭)  ·  Score[]  ·  Link[]
파기한다: 공고 이미지  ·  이력서 원문  ·  OCR 텍스트
```

**공고 원문 텍스트를 저장하지 않는다.** 이건 과제 CRITICAL("원문 복붙 금지")과 같은
요구인데, **이유가 둘로 갈린다.**

| | 왜 안 하나 |
|---|---|
| 과제 요구 | 이미지 파싱을 실제로 했는지 확인하려고 |
| 법적 구조 | 원문을 쌓으면 그게 곧 **DB 복제**다 |

**같은 규칙 하나가 두 요구를 동시에 만족한다.** 그리고 검산 **G4**(모든 조건에 이미지
좌표가 있어야 함)가 이걸 기계적으로 강제한다.

> 근거 그래프에 남는 것도 **좌표와 오프셋뿐**이다. `Evidence`는 이력서 원문이 있어야
> 렌더링되므로, 원문을 파기하면 **근거 문장은 고객사 쪽에서만 재구성된다.**
> 우리 DB만 털려도 이력서 내용이 나오지 않는다.

### ④ 결과 반환 — 우리는 결과를 안 쓴다

채점 결과는 위탁한 고객사만 조회한다. 다른 고객사에 노출되지 않고, 우리가 통계·학습에
쓰지 않는다.

**이게 트레이드오프다.** `docs/TRADEOFFS.md`에 적은 「사후 보정 불가」와 Kairen OS의
「Learning Loop 부재」가 **여기서 나온다.** 데이터를 안 쌓기로 했으니 모델이 좋아질
경로도 같이 닫힌다. 정확도와 법적 안전성을 맞바꾼 것이고, **채용 도메인에서는 후자를
택하는 게 맞다고 판단했다.**

## 4. 승인 게이트가 여기에 붙는다

이 구조에서 **고객사 승인**은 UX가 아니라 **법적 구조의 일부**다. 세 가지가 한 지점에서 만난다.

| 관점 | 승인이 하는 일 |
|---|---|
| **Kairen OS** | *"AI Platform은 후보를 만들고, Human Platform이 확정한다"* — `draft → human_validated` |
| **법적 구조** | 채점 기준이 **우리가 추론한 것**이 아니라 **고객사가 확정한 자기 기준**이 된다 |
| **과제 요구** | *"그 회사 기준이어야 하는데 그걸 어떻게 정할까"* 에 대한 답 |

우리 파서가 공고에서 뽑은 필수/우대 판정은 **추론**이다. 근거 등급 E1·E0가 붙은
항목은 특히 그렇다. 그 상태로 채점하면 **우리가 남의 채용 기준을 대신 정한 것**이 된다.

승인을 거치면 달라진다 — 고객사가 "이게 우리 기준이 맞다"고 확정한 것이므로,
**결과의 책임과 정당성이 기준을 정한 쪽에 있다.**

그래서 파이프라인이 실제로 멈춘다.

```
prepare(공고)  →  RubricProposal (전부 draft)
        ⛔ 승인 게이트
score(승인본, 이력서)  →  RunResult
```

`--skip-approval`로 건너뛸 수는 있지만, 그 결과에는 **「미승인」 표시가 지워지지 않는다.**

## 5. 데모(과제 제출본)와 프로덕션의 경계

과제는 사람인 API 크롤링을 **요구**하고, 동시에 그게 법적으로 문제라고 **말한다.**
모순이 아니라, 데모와 프로덕션이 다른 것이다. 코드가 그 차이를 드러내야 한다.

```python
class PostingSource(Protocol):          # 같은 인터페이스
    def list_postings(self, **q) -> list[PostingRef]: ...
    def fetch_images(self, posting_id: str) -> list[Path]: ...

class SaraminSource:      # 데모 전용 — pull. 프로덕션 금지
class LocalSource:        # 개발·테스트용 — 네트워크 없음
class ClientFeedSource:   # 프로덕션 — push 수신. 이번 과제에서 구현 안 함
```

`ClientFeedSource`는 **인터페이스와 docstring만 두고 본문은 `NotImplementedError`**다.
구현하지 않는 것이 과제 요구다. 하지만 **자리를 비워두면 설계했다는 증거가 없으므로**,
빈 클래스로 자리를 만든다.

`SaraminSource`에는 클래스 docstring 첫 줄에 이렇게 박는다.

```
데모 전용. 프로덕션에서 이 어댑터를 쓰면 안 된다 —
서비스 제공사가 직접 수집하는 구조가 되어 DB제작자의 권리·부정경쟁방지법·
이용약관 문제가 발생한다. 프로덕션 경로는 ClientFeedSource다.
docs/LEGAL_ARCHITECTURE.md 참조.
```

**`PostingRef.source_kind`가 `saramin_api | local | client_feed` 중 무엇인지 결과에
그대로 실린다.** UI가 `saramin_api`면 "데모 데이터" 배지를 띄운다. 데모 경로로 나온
결과를 프로덕션 결과와 헷갈릴 수 없게 만드는 것이 목적이다.

## 6. 이 구조가 못 푸는 것

정직하게 적는다. 이걸 안 적으면 설계가 아니라 홍보문이다.

1. **고객사가 남의 공고를 보내면 부분적으로만 잡는다.** 사람인 API로 `company` +
   `position.title` + `posting-date`를 대조해 **그런 공고가 실제로 게시돼 있는지**는
   확인한다(`docs/IMAGE_ACQUISITION.md` §3.5 역할①). 하지만 **보낸 이미지가 그 공고의
   이미지인지는 확인하지 못한다.** 권리 보증 조항은 나머지 책임을 옮길 뿐이다
2. **수탁 처리자도 유출 책임에서 자유롭지 않다.** 위탁받았다고 안전해지는 게 아니라
   **의무의 성격이 바뀔 뿐**이다
3. **원본을 파기하면 재현·감사가 어려워진다.** 채점 결과에 이의가 들어와도 원문이
   없어 재검증이 안 된다. `Evidence`의 오프셋만 남으므로 **고객사가 원본을 보관해야
   근거를 복원**할 수 있다 — 이건 고객사에 부담을 넘긴 것이다
4. **데모 경로의 이미지 취득은 API 권리 범위 밖이다.** 주의사항이
   *"제공하는 범위 내에서 ... 제한된 권리"*라고 하는데 API가 이미지를 제공하지 않으므로,
   **금지를 어긴 게 아니라 허락받은 적이 없는 행위**다. 스크래핑 금지 조항이 약관 전문에
   있는지는 **확인하지 못했다** (`docs/IMAGE_ACQUISITION.md` §2)
5. **데모 이미지와 프로덕션 이미지가 같은 파일이 아니다.** 사람인 CDN 사본은 리사이즈·
   재압축된 것이라 해상도·분할이 다르다. 그래서 `BBox`에 기준 이미지 크기를 같이 저장하지
   않으면 **데모에서 만든 근거 좌표가 원본 위에서 엉뚱한 자리를 가리킨다**
5. **법률 자문을 받지 않았다.** 이 문서는 설계 문서지 법적 판단이 아니다

## 7. README에 옮길 때

한 문장으로 줄이면 이렇다.

> **데이터의 이동 방향을 뒤집어 권리자를 건너뛰지 않게 만들고, 우리 쪽에는 원본을
> 남기지 않는다. 그리고 채점 기준을 고객사가 확정하게 해서, 우리가 남의 채용 기준을
> 대신 정하지 않게 한다.**

다이어그램은 §3의 4개 경계 그림을 쓴다. 못 푸는 것(§6)을 **반드시 같이 적는다** —
과제 평가 기준이 *"AI가 만들어준 결과물을 그대로 제출하기보다, 문제를 어떻게 정의하고
어떤 판단을 더했는지"*이기 때문이다.
