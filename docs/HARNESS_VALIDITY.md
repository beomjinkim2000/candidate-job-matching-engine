# 하네스가 실제로 효과가 있는가 — 실측

> **이 문서만 성격이 다르다 — 과제 산출물이 아니라 내 작업 도구를 고친 기록이다.**
>
> 심사(`HARNESS_SCOREBOARD.md`)는 「계획이 좋은가」를 물었다. 이 문서는
> **「그 계획이 실행 단계까지 제대로 전달되는가」**를 잰다. 둘은 다른 질문이고,
> 후자를 아무도 안 보고 있었다.
>
> 대상인 `scripts/execute.py`는 **제출 범위에 없다.** 그래서 이 문서는 코드 없이 읽어야 한다.
> 남긴 이유는 하나다 — **측정하지 않으면 「잘 되고 있다」가 기본값이 된다**는 것을
> 실물로 확인한 기록이라서.

---

**심사는 「계획이 좋은가」를 묻는다. 이 문서는 「실행기가 그 계획을 제대로 나르는가」를 묻는다.**
둘은 다른 질문이고, 심사위원 8명이 전부 후자를 안 봤다 — 그들이 받은 대상이 `step*.md`였기
때문이다. 실행기(`scripts/execute.py`)는 아무도 안 읽었다.

측정 시각: 2026-09-01 03:2x KST.

---

## 발견 1 — 가드레일이 step마다 107,806자였다

`scripts/execute.py:177` `_load_guardrails()`가 **`CLAUDE.md` + `docs/*.md` 전부**를
매 step 프롬프트에 넣고 있었다.

| | 실측 |
|---|---|
| 가드레일 크기 | **107,806자** ≈ 72,000 토큰 |
| step 본문 평균 | 5,549자 |
| **1 step 프롬프트** | **≈ 75,570 토큰** |
| **14 step 전체** | **≈ 1,058,000 토큰** |
| 재시도 3회 시 | 최대 **×3** |

### 무엇이 들어가고 있었나

`docs/`에 있다는 이유만으로 들어간 것들:

| 문서 | 크기 | 왜 문제인가 |
|---|---|---|
| `HARNESS_SCOREBOARD.md` | 7,720자 | **심사 스코어보드다.** 구현 세션에 「네 계획은 51/100, veto 4건」을 알려줄 이유가 없다. 도움이 안 되는 정도가 아니라 **해로울 수 있다** |
| `RUBRIC_GENERATION_EVIDENCE.md` | 8,806자 | 문헌 검토 근거. 코드를 쓰는 세션이 쓸 일이 없다 |
| `SCORING_CRITERIA_EXPLAINED.md` | 6,283자 | `SCORING_CRITERIA.md`의 **쉬운 설명판.** 사람이 읽으라고 만든 것이다. 같은 내용이 두 번 들어갔다 |
| `IMAGE_ACQUISITION.md` | 8,365자 | step 2 전용인데 14개 step 전부에 들어갔다 |
| `EVIDENCE_IDEAS.md` | 10,624자 | step 12가 「이 step의 명세다」라고 지목한 문서. 나머지 13개 step엔 무의미 |

### 이게 왜 설계 위반인가

`.claude/commands/harness.md`의 step 설계 원칙 3번이 **「사전 준비 강제 — 관련 문서 경로와
이전 step에서 생성된 파일 경로를 명시한다」**이다. 그래서 step 파일마다 **「읽어야 할 파일」**
절이 있다.

**그런데 실행기가 전부를 미리 주입하면 그 절이 무의미해진다.** step 3이 「`docs/OCR_EVIDENCE.md`를
읽어라」라고 적어놔도, 이미 프롬프트 앞에 `docs/` 전체가 들어가 있으면 무엇이 중요한지가 사라진다.
**하네스가 자기 설계 원칙을 자기 실행기로 무력화하고 있었다.**

### 고친 것

`_load_guardrails()`가 **`docs/.guardrails` 매니페스트**를 읽는다. 없으면 전부 넣는다
(원래 동작 — 기존 테스트 7개가 그 동작을 덮고 있고 전부 통과한다).

가드레일에 남긴 기준: **「이 문서를 안 읽으면 *어느 step이든* 규칙을 어길 수 있는가」**
「step N이 이걸 알아야 한다」면 답은 아니다 — step N의 읽기 목록에 적는다.

| | 이전 | 이후 |
|---|---|---|
| 가드레일 | 107,806자 (~72k 토큰) | **13,057자 (~8.7k 토큰)** |
| 14 step 전체 | ~1,058,000 토큰 | **~174,000 토큰** |
| **절감** | | **884,000 토큰** (재시도 3회면 ×3) |

남긴 6개: `CLAUDE.md`(과제 CRITICAL) · `docs/CLAUDE.md`(문서 지도) · `PRD` · `ARCHITECTURE` ·
`ADR`(기술 스택) · `SCHEDULE`(마감·분기) · `COST_BUDGET`(호출 상한).
뺀 이유는 `docs/.guardrails` 안에 문서별로 적혀 있다.

테스트 4개 추가 (`scripts/test_execute.py`): 매니페스트가 목록만 고르는지 · 주석·빈 줄을
무시하는지 · **없는 파일을 조용히 넘기지 않고 경고하는지** · 전부 뺐을 때 `CLAUDE.md`만 남는지.
**기존 7개 + 신규 4개 = 11개 전부 통과.**

## 발견 2 — 이 절감이 예산에 미치는 영향

`docs/COST_BUDGET.md`는 **OpenAI 호출**만 계산한다 (완주 ≈117회). 하네스 실행기는 **다른 예산**을
쓴다 — `claude -p` 서브프로세스다(`execute.py:238`). 그건 과제가 준 $5와 별개다.

**그래도 세어야 하는 이유**: 88만 토큰은 컨텍스트 한도에 부딪히는 크기다. step 하나가 75k
토큰으로 시작하면 실제 작업 여유가 그만큼 줄고, **재시도할수록 나빠진다.** 실행기가 3회
재시도하며 이전 에러를 프롬프트에 누적하므로(`execute.py:206-209`) 3번째 시도가 가장 무겁다.

## 발견 3 — 하네스가 **한 step도 못 돌고 있었다**

**심사위원 8명이 3라운드 동안 못 잡았다.** 그들이 받은 대상이 `step*.md`였고,
`scripts/execute.py`와 레포 상태는 아무도 안 봤기 때문이다.

```
$ git rev-parse --is-inside-work-tree
fatal: not a git repository
```

`execute.py:113` `_checkout_branch()`는 첫 줄에서 `git rev-parse --abbrev-ref HEAD`를
부르고 **rc가 0이 아니면 `sys.exit(1)`**한다. 즉 `python3 scripts/execute.py matching-engine`은
step 0을 시작조차 못 하고 죽는다.

**`git init`만으로도 부족하다.** 커밋이 하나도 없는 레포에서 같은 명령은 **rc 128**이다
(`fatal: ambiguous argument 'HEAD'`). **초기 커밋이 있어야 비로소 rc 0이 된다.**

| | 이전 | 이후 |
|---|---|---|
| `git rev-parse --abbrev-ref HEAD` | rc **128** | rc **0** (`main`) |
| `execute.py` 진입 | `sys.exit(1)` | 진행 |

### 고친 것

`git init` + 브랜치명을 `main`으로 + 초기 커밋 1개 (`0f32ea2`, 추적 파일 57개).

무시 규칙을 **파일을 만들지 않고** 검사했다 (`git check-ignore --no-index`):

| 경로 | 판정 |
|---|---|
| 키 파일 · 키 파일 변형 | 무시 ✓ |
| `.claude/settings.json` · `harness.toml` · `hooks/` · `out/` | 무시 ✓ |
| `data/postings/*/provenance.json` · `data/resumes/**` | **추적** ✓ (제출물이므로 맞다) |
| `data/postings/*/img_*.png` | 현재 **추적** — `step0.md`가 무시 패턴을 넣는다 |

마지막 행이 의도된 순서다. `step0.md`가 `.gitignore` 소유자이고, **이미지만 파일 단위로**
빼도록 못박혀 있다 (veto V6 대응).

### 이 발견이 말하는 것

**「계획을 심사한다」와 「실행 가능한지 본다」는 다른 일이다.** 심사위원 8명이 3라운드에
걸쳐 72점까지 끌어올린 계획이, 실행기 관점에서는 **0 step**이었다.

`plan-review` 스킬이 대상을 계획문서로 한정하는 것은 옳지만, **그 계획을 나르는 도구는
아무도 안 본다**는 사각이 생긴다. 이 문서가 그 사각을 메우려는 것이고,
아래 「아직 검증 안 된 것」이 그 사각의 남은 부분이다.

## 이 검증이 틀리는 조건

- **토큰 환산은 한글 1.5자/토큰 어림이다.** 실제 토크나이저는 다르다. 자릿수는 맞지만
  ±30%는 틀릴 수 있다. 절감의 **비율**(107,806 → 13,057, 88% 감소)은 어림에 영향받지 않는다
- **매니페스트가 너무 공격적일 수 있다.** 뺀 문서 중 하나가 실제로 「어느 step이든 어기면
  안 되는 규칙」을 담고 있었다면 그 step이 규칙을 어긴다. **판정 근거는 각 step의
  「읽어야 할 파일」이 그 문서를 지정하고 있는가**였고, 문서별로 `.guardrails`에 적어뒀다 —
  틀렸으면 어디가 틀렸는지 추적할 수 있다
- **`docs/`에 새 문서를 추가하면 이제 자동으로 안 들어간다.** 이건 의도한 동작이지만,
  「추가했는데 왜 안 먹지」의 원인이 될 수 있다. `.guardrails` 상단에 그 사실을 적어뒀다
