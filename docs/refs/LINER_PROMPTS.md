## 프롬프트 ① — 핵심. 채점 기준을 기계가 써도 되는가

> **우선순위 1.** 이 하나만 돌려도 재설계 판단은 가능하다.

```
LLM이 채점 루브릭(rubric, 평가 기준표)을 자동 생성하는 것이 사람이 작성한 루브릭과
비교해 어떤 성능·신뢰도 차이를 보이는지 실증 근거를 정리해줘.

구체적으로 알고 싶은 것:

1. LLM이 생성한 루브릭 vs 전문가가 작성한 루브릭을 직접 비교한 연구나 실무 보고가 있는가?
   - 채점 결과의 인간 평가자와의 합치도(agreement, Cohen's kappa, QWK, 상관계수)가 얼마나 차이 나는가
   - 어느 도메인에서 비교됐는가 (에세이 채점, 코드 리뷰, 고객 응대 품질, 채용 등)

2. 루브릭을 "항목별 맞춤 기준점"으로 쓰는 것과 "전 항목 공통 템플릿"으로 쓰는 것의 차이:
   - 평가 항목마다 다른 기준점 문구를 쓰는 방식(item-specific rubric)과
     모든 항목에 같은 기준점 문구를 쓰는 방식(generic/holistic rubric)의 신뢰도 비교
   - 교육 평가 문헌에서 analytic rubric vs holistic rubric 비교 결과
   - generic rubric이 특정 조건에서 오히려 나은 경우가 있는가

3. 루브릭 문구의 품질이 채점 결과에 미치는 영향의 크기:
   - 같은 뜻인데 표현만 바꿨을 때 점수가 얼마나 이동하는지 측정한 연구
   - LLM 채점자에서도 사람 평가자와 같은 크기의 영향이 나타나는가

4. 자동 생성 루브릭의 알려진 실패 모드:
   - 어떤 종류의 평가 항목에서 자동 생성이 특히 나쁜가
   - 생성된 기준이 순환 논리가 되거나(기준이 답을 이미 포함) 측정 불가능해지는 문제

5. 실무에서 실제로 쓰는 방식:
   - OpenAI Evals, Anthropic, LangSmith, Braintrust, Humanloop, Arize 등 평가 도구가
     루브릭을 어떻게 다루는지 (사람이 쓰게 하는가, 자동 생성을 지원하는가)
   - 자동 생성을 지원한다면 어떤 안전장치를 붙였는가 (사람 검토 단계 등)

[출처 규칙 붙이기]
```

**이 답으로 판정할 것**: 공통 템플릿을 유지할지, 항목별 기준점을 LLM에게 쓰게 하고
승인 게이트에서 사람이 고치게 할지.

## 프롬프트 ② — LLM-as-judge를 실제로 어떻게 운영하나

```
LLM-as-a-judge(LLM을 평가자로 쓰는 방식)의 신뢰성과 실무 운영 방법에 대한
연구 결과와 실제 기업의 운영 사례를 정리해줘.

구체적으로:

1. 알려진 체계적 편향(bias)과 그 크기:
   - position bias(제시 순서에 따른 편향) — 순서만 바꿨을 때 판정이 뒤집히는 비율
   - verbosity/length bias(긴 답을 선호) — 길이와 점수의 상관
   - self-preference bias(자기 모델 출력 선호)
   - 각각을 완화하는 검증된 방법과 그 효과 크기

2. 채점 방식별 신뢰도 비교:
   - 절대 점수 매기기(pointwise scoring)
   - 두 개를 비교하기(pairwise comparison)
   - 기준 답안을 주고 채점(reference-guided)
   - 체크리스트(checklist, 예/아니오 항목)
   위 네 가지 중 어느 것이 인간 합치도가 높고, 어떤 조건에서 그런가

3. 재현성:
   - 같은 입력을 반복했을 때 판정이 달라지는 비율(자기 일관성, self-consistency)
   - temperature 설정, 다수결(self-consistency voting)이 이를 얼마나 줄이는가
   - 실측 수치가 있는 출처를 우선

4. 여러 판정자를 쓰는 것의 효과:
   - LLM 판정자 여러 개를 앙상블할 때 실제로 얻는 정보량
   - 모델 간 상관 오차(correlated errors) 때문에 사람 여러 명과 다른 점
   - 서로 다른 제공사 모델을 섞는 것이 같은 제공사 여러 모델보다 나은가

5. 실무 운영 사례 (테크 블로그·공식 문서 환영):
   - 실제 프로덕션에서 LLM-as-judge를 쓰는 회사가 공개한 운영 방식
   - 판정자 출력에 근거·인용을 강제하는 것이 정확도에 도움이 되는가, 아니면 형식만 지키는가
   - "근거 먼저 쓰고 점수 나중"(reasoning-then-score) 순서의 효과를 측정한 결과

[출처 규칙 붙이기]
```

## 프롬프트 ③ — 채용에 AI를 실제로 적용한 시스템

```
채용 서류심사·지원자 스크리닝에 AI/LLM을 적용한 실제 시스템의 설계와
그에 대한 검증·규제 현황을 정리해줘. 한국 사례가 있으면 반드시 포함해줘.

구체적으로:

1. 실제 제품의 동작 방식:
   - HireVue, Eightfold AI, Workday, Greenhouse, LinkedIn Recruiter, SmartRecruiters 등이
     공개한 매칭·스코어링 방식 (공식 문서·기술 백서·엔지니어링 블로그 기준)
   - 점수를 산출하는가, 순위만 매기는가, 아니면 추천만 하는가
   - 사람이 개입하는 지점을 어디에 뒀는가

2. 검증 결과:
   - 이 시스템들의 예측 타당도나 인간 채용담당자와의 합치도를 측정한 독립 연구
   - 벤더 자체 발표와 독립 검증의 결과 차이

3. 알려진 실패와 편향 사고:
   - 실제로 문제가 드러난 사례 (Amazon 채용 AI 등) — 무엇이 원인이었는지
   - LLM 기반 이력서 스크리닝에서 이름·학교·성별 신호로 인한 편향을 측정한 최근 연구

4. 규제 요구사항:
   - 미국 NYC Local Law 144 (AEDT 편향 감사 의무) — 구체적으로 무엇을 요구하는가
   - EU AI Act에서 채용 AI의 분류와 그에 따르는 의무
   - 한국 — 채용절차법, 개인정보보호법상 자동화된 결정에 대한 권리,
     고용노동부의 블라인드 채용 지침이 AI 채용에 적용되는 방식
   - 「사람이 최종 결정한다」는 구조가 규제 요구를 실제로 만족시키는가

5. 설명가능성 요구:
   - 지원자에게 탈락 사유를 제공해야 하는 법적 의무가 있는 관할이 있는가
   - 실무에서 근거를 어떤 형태로 제공하는가

[출처 규칙 붙이기]
```

## 프롬프트 ④ — 이력서·직무기술서 매칭의 기술적 실태

> 우선순위 3. 여유 있으면.

```
이력서와 채용공고를 매칭해 점수를 매기는 시스템(resume-job matching)의
기술적 접근법과 각각의 성능을 정리해줘.

1. 접근법별 비교:
   - 키워드/규칙 기반, 임베딩 유사도, 학습된 랭커, LLM 직접 채점
   - 어느 방식이 어떤 지표에서 얼마나 나은가 (nDCG, precision@k, 인간 합치도 등)
   - 공개 벤치마크나 데이터셋이 있는가

2. LLM으로 이력서를 채점할 때 보고된 문제:
   - 없는 경험을 지어내거나 과대 해석하는 비율
   - 이력서 길이·서술 스타일이 점수에 미치는 영향
   - 프롬프트 인젝션 (이력서에 흰 글씨로 지시문을 심는 공격)에 대한 대응

3. 요구조건을 필수/우대로 분류하는 문제:
   - 공고 텍스트에서 요구조건의 강도를 자동 판정한 연구나 실무 사례
   - 정확도가 어느 정도이고 어떤 신호를 쓰는가

4. 구조화된 조건 추출:
   - 채용공고에서 스킬·경력 요건을 구조화 추출하는 표준 스키마나 온톨로지
```
