# 예산 — 완주 1회에 몇 회, 어느 모델, 얼마인가

과제가 준 OpenAI 예산은 **$5**다. 13개 step에서 「$5」를 6번 인용하면서 정작
**단위 작업당 호출수·모델명·단가가 한 건도 없었다.** 그 숫자 없이 세 개의 결정
(순서 편향 점검 끄기 · 소거 재채점 표본화 · 캐시 강제)을 내렸다. 이 문서가 그 숫자다.

## 1. 완주 1회 호출수 — 계산

「완주」 = 공고 2개 × 지원자 6명 = **12명 채점 + 랭킹 2개**.

| # | 무엇 | 계산 | 호출 |
|---|---|---|---|
| 1 | 헤더 역할 분류 (step 3-C) | 공고 2 × 1회 | **2** |
| 2 | 주장 추출 (step 12-B) | 이력서 12명 × 1회 | **12** |
| 3 | 심사위원 채점 (step 6) | 12명 × 판단항목 2개 × 심사위원 2명 | **48** |
| 4 | 3번째 심사위원 (이견 시) | 12 × 2 항목 중 이견률 **최악 100%** | **≤ 24** |
| 5 | 소거 재채점 (step 12-C) | 공고당 상위 3명 × 2공고 × 2항목 × 6조건¹ | **≤ 72 → 48로 상한** |
| | **합계 (최악)** | | **≤ 134** |
| | **합계 (이견 30% 가정)** | 2+12+48+7+48 | **≈ 117** |

¹ `s_full` · `s_ablate` · `s_placebo` ×3 · `s_only` = 6조건

**호출 상한을 코드로 잠근다** — `settings.max_total_calls = 200`. 넘으면
`CallBudget`이 예외를 던진다(step 6). 조용히 줄이지 않는다.

### 재실행 비용

| 무엇을 바꿨나 | 다시 부르는 것 | 호출 |
|---|---|---|
| OCR 임계값·파싱 규칙 | 없음 — `ocr.json` 재사용, 헤더 역할도 캐시 | **0** |
| 공고 이미지 교체 | 헤더 분류만 | 2 |
| 이력서 수정 | 그 이력서의 주장 추출 + 채점 | 1 + 4 |
| 루브릭 가중치 | 없음 — 산술이다 | **0** |
| 12-A 등수 뒤집기 | 없음 — **전부 산술** | **0** |

**규칙 변경이 0회인 것이 파일 3분할(`ocr.json` / `requirements.json`)의 실익이다.**
합쳐 뒀으면 임계값 하나 고칠 때마다 OCR을 다시 돌려야 했다.

## 2. 모델과 단가

**모델명을 코드에 박지 않는다.** `settings.header_model` · `settings.judge_model`에서
오고, 단가도 `settings.price_in_per_1m` · `price_out_per_1m`에서 온다.

| 자리 | 요구 | 왜 |
|---|---|---|
| 헤더 역할 분류 | **가장 싼 것.** 입력 <1,000토큰, 출력 <300 | 문자열 4~8개를 5종으로 분류. 어려운 판단이 아니다 |
| 심사위원 채점 | **중간 이상.** 입력 ~2,500토큰(루브릭+이력서), 출력 ~400 | 근거 인용 + 판단. 여기서 아끼면 채점이 무너진다 |
| 소거 재채점 | 심사위원과 **같은 모델** | 다른 모델을 쓰면 Δ가 소거 효과인지 모델 차이인지 모른다 |

**단가는 이 문서에 숫자로 박지 않는다.** 공식 가격표가 바뀌고, 틀린 숫자를 박아두면
그게 근거처럼 읽힌다. 대신 **런타임에 실측한다**:

```python
class CallBudget:
    def spend(self, in_tokens: int, out_tokens: int) -> None: ...
    def usd(self) -> float: ...    # settings의 단가 × 실제 토큰
```

`data/.judge_usage.json`에 **호출수·토큰·환산 USD를 누적**하고, 완주 후
`RunResult.cost`에 실린다. **결과 화면에 「이 결과를 만드는 데 n회 / $x」가 표시된다.**

> 「얼마인가」의 정답은 추정치가 아니라 **실측치**여야 한다. 완주 1회 후 이 문서 §4에
> 실측을 적는다. 그전까지 §3은 추정이라고 적혀 있다.

## 3. 토큰 추정 (실측 전)

| 항목 | 입력 | 출력 | 회 | 입력 계 | 출력 계 |
|---|---|---|---|---|---|
| 헤더 분류 | 1,000 | 300 | 2 | 2,000 | 600 |
| 주장 추출 | 1,800 | 700 | 12 | 21,600 | 8,400 |
| 심사위원 | 2,500 | 400 | 55 | 137,500 | 22,000 |
| 소거 재채점 | 2,200 | 200 | 48 | 105,600 | 9,600 |
| **계** | | | **117** | **≈ 267k** | **≈ 41k** |

**이미지 토큰이 0인 것이 이 표의 특징이다.** 이전 설계(VLM 파싱)였다면 고해상도 공고
이미지 2장이 여기 들어왔다 — 세로로 긴 공고라 타일 수가 많아 파싱 한 번에만 수천 토큰이
들었을 것이다. **OCR로 바꾼 결정이 예산에서도 이득**이었다.

## 4. 실측

### 4-1. OpenAI (`data/.judge_usage.json`) — 2026-09-01 12:00, step 7 진행 중

| | 값 |
|---|---|
| 호출수 | **149** (상한 200의 74%) |
| 입력 토큰 | 278,517 |
| 출력 토큰 | 25,824 |
| USD (아래 단가로 환산) | **약 $0.96** |
| 예산 잔액 | $5 중 **약 $4.04** |

환산은 §2의 공식 단가(gpt-4o $2.50/$10.00 per 1M)로 손계산했다. 대부분이 심사위원
호출이라 gpt-4o로 잡았고, 헤더 분류(gpt-4o-mini) 몫은 반올림에 묻힌다.
**코드는 여전히 USD를 0으로 보고한다** — 단가를 코드에 박지 않기로 한 결정(§2)이고,
`.env`에 `MATCHING_PRICE_IN_PER_1M`·`MATCHING_PRICE_OUT_PER_1M`을 넣으면 켜진다.

> ⚠️ **§1의 추정이 빗나갔다.** 「완주 1회 최악 134회」로 잡았는데 **완주 전에 이미
> 149회**다. 원인 둘: (a) 재현성 σ 측정을 표본 포화 때문에 **두 번** 돌렸다(44×2 + 8),
> (b) step 5·6·7이 각자 실행 검증을 하면서 파이프라인을 여러 번 돌렸다.
> 상한 200은 **돈이 아니라 실수를 막는 난간**이었는데, 그 난간이 완주 전에 걸릴
> 참이었다. 호출당 실측 단가가 **$0.0064**이므로 잔액 $4.04는 **약 630회**에 해당한다 —
> 돈은 넉넉하고 난간만 낮았다. `max_total_calls`를 600으로 올렸다.

### 4-2. Claude (하네스 구현 세션) — 같은 시각

| | 값 |
|---|---|
| 세션 수 | 39개 (step별 워커 + 심사위원 + 리드) |
| 총 토큰 | **600.2M** |
| 그중 캐시 읽기 | 562.0M (**93.6%**) |
| 순수 입력 / 출력 | 6,801 / 6.3M |

**93.6%가 캐시 읽기**다. 같은 값을 반복 청구한 것이 아니라 할인 단가로 청구된
재사용분이고, 이 비율이 낮았다면 같은 작업이 몇 배로 비쌌다. 가드레일 주입을
`docs/.guardrails`로 줄인 것(107,806자 → 13,057자)이 여기 반영돼 있다.

### 4-3. 벽시계 — step별

| step | 소요 | | step | 소요 |
|---|---|---|---|---|
| 0 project-setup | 7분 | | 4 rubric-builder | 10분 |
| 1 core-model | 7분 | | 5 fact-scorer | 18분 |
| 2 posting-source | 14분 | | 6 judge-layer | 43분 |
| 3 posting-parser | **29분** | | 7 aggregate-rank | 진행 중 |
| 10 mock-resumes | 19분 | | **8개 합계** | **147분 (2.5시간)** |

**step 3의 `index.json` 기록은 377분이지만 실제 작업은 29분이다.** 04:32에
`OPENAI_API_KEY` 없음으로 blocked됐고 10:20에 키를 받아 재개했다 — 나머지 348분은
**대기**이지 계산이 아니다. 이 구분을 안 하면 「파서 하나에 6시간」이라는 거짓 수치가 남는다.

**한 step은 평균 18분**이고, 그동안 Claude 세션 하나가 코드 300~1,500줄과 테스트를
쓰고 검증까지 돌린다. 남은 6개(7·8·9·11·12·13)는 **약 1.8시간** 예상.

> **이 표는 「제품이 느리다」가 아니다.** 여기 적힌 것은 **엔진을 만드는 데** 걸린
> 시간이고 한 번만 든다. **제품이 공고 1건 + 지원자 6명을 채점하는 데는 2~4분**이다
> (§3, step 7 실측으로 갱신 예정).

## 5. 예산이 모자랄 때 버리는 순서

`step12.md:14`의 순서를 예산 관점에서 다시 쓴 것이다. **위에서부터 버린다.**

| 순 | 버리는 것 | 아끼는 호출 | 잃는 것 |
|---|---|---|---|
| 1 | **12-C 소거 재채점** | 48 | 「근거 충실도」 배지. 인용 유효성(G2)은 남는다 |
| 2 | **12-B 판단유탈 대장** | 12 | 미처리 주장 검산(G6) |
| 3 | **3번째 심사위원** (임계를 3으로 올림) | ≤24 | 이견 큰 항목의 정밀도 |
| 4 | **심사위원 1명으로** | 24 | 판정 안정성. **여기부터는 설계가 바뀐다** |
| 5 | **`--no-judge`** (판단 층 생략) | 55+ | 65점 배점 전체. **제출물로 성립 안 함** |

**4번부터는 「줄인다」가 아니라 「다른 시스템이 된다」.** 4·5를 쓰면 결과에 그 사실이
반드시 표시돼야 한다 (`RunResult`에 `degraded_mode`).

## 6. 6개월 뒤 규모에서

고객사 3곳 × 월 500명이면 채점만 월 500×3×2항목×2명 = **6,000회**. 12-C를 켜면
그 8배다. 단가가 그대로여도 **채점 1건당 단가는 내려가지 않는다** — 이력서마다 토큰이
새로 들어가므로 규모의 경제가 없다. 캐시가 먹는 것은 **공고 파싱뿐**이고 그건 원래 싸다.

**그래서 세 번째로 버릴 것의 이름은 「3번째 심사위원」이다** (위 표 3번). 이견 임계를
올리면 호출이 선형으로 준다. 그다음은 12-C를 표본에서 **아예 끄는 것**이고,
그 이후로는 배점 구조를 바꿔야 한다 — 이건 운영이 아니라 설계 결정이다.

유지 주체와 운영 비용의 나머지는 `docs/OPERATIONS.md`.
