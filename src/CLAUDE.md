# src/ — 구현 규칙

**구현 전 `docs/RUBRIC_DESIGN.md`를 읽는다.** 아래 결정은 문헌 검토 2회를 거쳐 확정된 것이다.
**재논의하지 않는다.**

## 아키텍처 — 3층

```
0층 게이트 (코드, 통과/탈락)
    면허·법정 자격증만. 미충족 시 탈락 사유를 명시하고 랭킹에서 분리
        ↓ 통과자만
1층 사실 채점 (코드, 결정적)                     35점
    필수 스킬 커버리지 20 / 우대사항 10 / 경력 연차 5
        ↓
2층 판단 채점 (심사위원 에이전트 + 루브릭)        65점
    경험의 직무관련성·깊이 40 / 성과 서술의 실질성 25
        ↓
    가중합산 → 0~100점 + 축별 근거
```

**왜 이 배분인가**: 세는 방식(Point Method) 타당도 r≈0.15, 판단 방식(행동일치법) r≈0.48.
세는 축이 판단 축보다 배점이 높으면 근거에 어긋난다.

## 근거 모델 — Object + Link

**근거는 문장이 아니라 Link다.** 근거 문장은 Link 위에 렌더링하는 결과물이지 저장 단위가
아니다. 근거는 `Score → grounded_in → Evidence → supports → Criterion → derived_from →
Requirement → extracted_from → 공고 이미지 좌표`로 끝까지 이어져야 한다.


| Object | 담는 것 | 필수 필드 |
|---|---|---|
| `Requirement` | 공고에서 뽑은 조건 1개 | `kind`(필수/우대), `evidence_grade`, `source_bbox`, `source_span`, `review_status` |
| `Criterion` | 루브릭 항목 1개 | `anchors`(1/3/5점 문구), `weight`, `review_status` |
| `Evidence` | 이력서 원문의 한 구간 | `resume_id`, `span`(시작·끝 문자 오프셋) |
| `Score` | 항목 1개의 점수 | `value`, `layer`(gate/fact/judgment), `judge_id` |
| `Link` | 위 Object 사이의 관계 | `src`, `rel`, `dst` |

`rel` 종류는 5개로 고정한다 — `extracted_from` · `derived_from` · `supports` ·
`grounded_in` · `contradicts`. 늘리지 않는다.

### review_status — AI 초안과 사람 확정을 섞지 않는다

모든 `Requirement`·`Criterion`은 `draft`로 생성된다. 고객사(공고 게시 회사)가 승인한
항목만 `human_validated`가 된다. **UI는 이 둘을 반드시 다르게 표시한다.**

### 승인 게이트 — 파이프라인이 실제로 멈춘다

**`review_status`는 필드가 아니라 절차다.** 승인이 코드 어딘가의 선택 함수로만 있으면
`human_validated`에 도달할 경로가 없다. 그래서 파이프라인을 **두 동강** 낸다.

```
prepare(posting)  →  RubricProposal   전부 draft
        ⛔ 여기서 멈춘다 — 사람이 승인해야 다음이 없다
score(approved, resumes)  →  RunResult
```

- `prepare()`는 채점을 하지 않는다. 이력서를 아예 받지 않는다
- `score()`는 `RubricProposal.approved_at`이 없으면 `ApprovalRequired`를 던진다
- **건너뛰려면 명시적으로** `--skip-approval`을 줘야 하고, 그때는 `RunResult.unapproved =
  True`가 되어 **결과 전체와 UI 상단에 「미승인」 표시**가 붙는다. 조용히 지나갈 수 없다

승인 화면에서 고객사가 할 수 있는 것은 셋이다 — **항목 승인 / 필수·우대 뒤집기 /
항목 삭제.** 가중치는 못 만진다(직군 무관 일반화를 지키기 위해). 뒤집기와 삭제는
`Link`로 원래 판정을 남긴다 — `C-03 ──contradicts──▶ R-03`.

**승인이 점수 계산식을 바꾸지 않는다.** 필수/우대 판정과 항목 유무는 바뀌지만,
가중치·기준점·매처는 그대로다.

## 채택한 근거 확장 3가지

`docs/EVIDENCE_IDEAS.md`가 정본이다. 셋 다 **채택**했고 `phases/matching-engine/step12.md`가
구현 명세다. 넣는 순서는 **③ → ① → ②** (비용 오름차순).

| | 무엇 | 어디에 붙나 | 비용 |
|---|---|---|---|
| ③ 등수 뒤집기 최소 편집 | 인접 순위를 넘기는 최소 조건 집합 + 동점권 | `pipeline/contrast.py` | LLM 0회 |
| ① 판단유탈 대장 | 이력서 주장을 원자 단위로 추출 → 전부 처리했는지 검산 | `pipeline/ledger.py` | 이력서당 1회 |
| ② 근거 소거 재채점 | 인용을 지우고 재채점 + **플라시보 대조군** | `judge/ablation.py` | 표본만 |

**①이 검산에 G6을 추가한다** — 미처리 주장이 남으면 그 지원자는 랭킹에 못 올라간다.

**②가 UI에 배지를 하나 더 만든다.** 「인용 유효」(G2)와 「근거 충실도」(②)를 **절대
합치지 마라.** 전자가 100%여도 후자는 0일 수 있다. 인용 실재율을 측정한 연구에서
어떤 모델도 0.475를 못 넘었는데 **그동안 출력 형식은 계속 규격을 지켰다.**

### evidence_grade — 근거 수준을 점수와 분리한다

| 등급 | 뜻 | 판정 사다리 |
|---|---|---|
| `E2` | 공고에 명시됨 | 1단계(섹션) · 2단계(수식어) |
| `E1` | 공고 구조에서 추론함 | 3단계(담당업무 대응) · 4단계(반복) |
| `E0` | 근거 없음 | 5단계(신호 없음 → 기본값) |

**등급을 점수에 곱하지 않는다.** 표시만 한다. 곱하면 점수가 낮은 이유가 적합도 때문인지
근거 부족 때문인지 구분이 사라진다.

### 검산 (Governance) — 결과 출력 전 전부 통과해야 한다

| | 규칙 | 위반 시 |
|---|---|---|
| G1 | 모든 `Score`에 `grounded_in` Link가 1개 이상 | 차단 |
| G2 | 모든 `Evidence`의 span이 이력서 원문 문자열에 실재 | 차단 |
| G3 | 모든 `Criterion`에 `derived_from` Requirement 존재 | 차단 |
| G4 | 모든 `Requirement`에 `source_bbox` 존재 | 차단 |
| G5 | 모든 `Requirement`에 `evidence_grade` 존재 | 차단 |
| G6 | 모든 `Claim`이 `채택`/`배척`/`무관` 중 하나 (미처리 0개) | **그 지원자만** 랭킹 보류 |
| G7 | 승인이 **현재 공고 revision**에 대한 것 (`modification-timestamp` 일치) · 공고가 `active` | 차단 (`ApprovalStale`) |

**G4가 "공고 원문을 복붙하지 않았다"의 기계적 증명이다.** 좌표 없는 조건이 있으면 그건
이미지에서 나온 것이 아니다. 이 검산은 테스트가 아니라 **런타임 게이트**다.

## 절대 규칙

- **세는 것은 코드가, 판단하는 것은 심사위원이.** 심사위원에게 "경력 5년 맞나?"를 묻지 않는다.
  같은 질문 50회 반복 시 판정이 13.6% 뒤집힌다는 실측이 있다.
- **직군·스킬셋을 하드코딩하지 않는다.** 루브릭 항목은 파싱된 공고 조건에서 생성한다.
  고정하는 것은 기준점의 **패턴**뿐이고, 패턴은 **둘**이다 (`rubric/anchors.py`).
  어느 쪽을 쓸지는 조건의 갈래가 정한다 (`rubric/branch.py`).
  - 서술형 (`graded` · `term`) — 정도가 있는 조건
    - 1점 — 관련 경험이 없거나, 있어도 구체적 행동 서술이 없음
    - 3점 — 제시하나 서술이 추상적이고 본인 역할·성과가 불명확함
    - 5점 — 본인의 역할 · 취한 행동 · 달성한 성과가 명확히 서술됨
  - 충족형 (`binary`) — 예/아니오인데 이력서가 **다른 말**로 적는 조건.
    **행동·성과 서술을 추가로 요구하지 않는다** — 요구하면 구조적으로 만점이 안 나온다
    - 1점 — 충족한다고 볼 근거가 이력서에 없거나, 충족하지 않는다고 적혀 있음
    - 3점 — 충족하는 것으로 보이나 이력서만으로 단정할 수 없음
    - 5점 — 충족한다는 것이 이력서에 분명히 드러남 (표현이 조건과 달라도 됨)
- **가중치·게이트 조건은 설정값으로 외부화한다.** 코드에 상수로 박지 않는다.
- **조건마다 공고 원문의 위치(문자 오프셋 + 이미지 좌표)를 함께 저장한다.**
  근거 추적에 쓰이고, "원문을 복붙하지 않았다"는 증명이 된다.
- **원본을 적재하지 않는다.** 공고 이미지·이력서 원문·OCR 텍스트는 처리 후 파기하고,
  구조화된 조건·루브릭·점수·Link만 남긴다. 이유가 둘이다 — 과제 CRITICAL(원문 복붙 금지)
  이면서, **원문을 쌓으면 그게 DB 복제**다 (`docs/LEGAL_ARCHITECTURE.md`).
- **경력 연차는 포화함수로 처리한다.** 선형 비례 금지 — 요구 3년에 10년 보유가 3배 우수하지 않다.
- **학력은 고정 축이 아니다.** 공고가 명시적으로 요구할 때만 켜지는 조건부 축
  (블라인드 채용 금지 항목).
- **스코어링 전에 민감 속성을 마스킹한다** — 이름·성별·나이·출신지·학력·사진.

## 필수/우대 판정

**신호는 가중치 추정이 아니라 필수/우대 판정에 쓴다.** 가중치는 등수를 거의 바꾸지 않지만,
필수/우대는 크게 바꾼다.

판정 순서 — 위에서부터, 결론이 나면 멈춘다.

1. 섹션이 명확한가 (자격요건 / 우대사항) → 확정. **가장 신뢰도 높음**
2. 수식어가 있는가 ("필수·반드시" / "우대·있으면") → 확정
3. 담당업무에 대응하는 일이 있는가 → 필수 쪽으로
4. 2회 이상 반복 등장하는가 → 필수 쪽으로
5. 시각적으로 강조됐는가 → **가설.** 판정을 바꾸지 않고 신뢰도만 낮춘다

3~5까지 간 항목은 **"모호함"으로 표시**한다. 조용히 결정하지 않는다.

## 파싱 — OCR이 주, LLM은 헤더 분류만 (2026-08-31 확정)

**이미지를 LLM에 보내지 않는다.** 좌표의 출처는 OCR 하나뿐이다.

| 단계 | 누가 | 결정적인가 | 비용 |
|---|---|---|---|
| 1. 줄 + 좌표 읽기 | **PaddleOCR** (로컬·전 OS). 맥 개발용으로 macOS Vision 선택 가능 | ✅ | 0 |
| 2. 섹션·항목 나누기 | **코드** — x 들여쓰기(헤더/항목) · 불릿(`·` `-` `•` `※`) · 이어지는 줄 병합 | ✅ | 0 |
| 3. 헤더 역할 분류 | **LLM, 텍스트만** — 헤더 문자열 몇 개 → `requirement`/`preferred`/`duty`/`context`/`excluded` | ❌ | 공고당 1회 |
| 4. 필수/우대 최종 판정 | **코드 사다리** (아래 「필수/우대 판정」) | ✅ | 0 |

> **1단계가 ~~EasyOCR~~에서 PaddleOCR로 바뀌었다 (2026-09-01 01:00).** 같은 이미지에서
> EasyOCR 평균 신뢰도가 **0.396**이었고 2배·3배로 키워도 0.382/0.396이라 해상도가 아니라
> 모델 문제였다. PaddleOCR은 0.936. 실측은 `docs/OCR_EVIDENCE.md` §1.
>
> **2단계에서 ~~「bbox 세로 크기로 헤더를 가른다」~~를 뺐다 (같은 날).** 실측 공고의
> **모든 줄이 12~14px**였다 — 헤더는 크기가 아니라 **굵기와 색**으로 구분돼 있었고
> **OCR은 굵기도 색도 주지 않는다.** 확정된 규칙인 줄 알았고 틀렸다.
> 남은 기하 신호는 **x 들여쓰기 하나**이고, 그건 살아 있었다 (`docs/OCR_EVIDENCE.md` §2~3).
>
> 그 결과 **판정 사다리 5단계(시각 강조)는 현재 경로에서 발동하지 않는다.**
> 자리는 두되 `emphasized`는 항상 `False`이고, `ParseReport.emphasis_available=False`로
> 결과에 적는다. **「구현했는데 안 쓴다」가 아니라 「입력이 없다」**이다.

**3단계에 이미지를 보내지 않는다.** 헤더 문자열 4~5개만 보낸다 — 이미지 토큰이 비싼 부분인데
그걸 안 쓴다. 그리고 **사전 하드코딩(`{자격요건, 지원자격, ...}`)을 피하는 유일한 방법**이다.
사전을 쓰면 「이런 분을 찾습니다」 같은 표현에 조용히 실패한다.

**왜 VLM을 안 쓰나** — VLM은 신뢰할 만한 bbox를 못 준다. 물으면 그럴듯한 값을 지어낸다.
그러면 **G4가 지어낸 좌표를 검사하는 꼴**이 되어 검산이 무의미해진다.
그리고 OCR은 못 읽으면 **침묵**하는데 VLM은 **문맥으로 채운다.** 그 비대칭이 환각을 막는다.

**폴백**: 2단계가 섹션을 못 찾으면(색으로만 구분한 헤더 · 다단 레이아웃 · 표) **그때만 VLM 1회**.
어느 경로로 갔는지 `parse_mode`로 결과에 남긴다.

**전제 조건**: OCR이 읽히는 이미지여야 한다. 안 읽히면 매칭이 실패하고 좌표가 없어
**G4가 전부 차단**한다. 완화하지 않는다 — 느슨한 매칭은 지어낸 것을 통과시킨다.
공고를 고를 때 이 조건을 확인하고, 확인했다는 사실을 문서에 적는다.

### 한 공고에 직무가 여러 개일 때

확보한 공고 A(KT)는 `직무 | 수행업무 및 우대사항 | 근무지` **3열 표**에 직무 3개가 들어 있다.
줄 단위 OCR은 **셀 소속을 잃고**, 그러면 다른 직무의 조건이 지원자에게 걸려 **점수가 틀린다.**

**표를 표로 파싱하지 않는다.** 필요한 건 셀 격자가 아니라 **관심 직무의 y 구간** 하나다.
대상 직무는 CLI 인자 `--position`으로 들어오고, 그 라벨의 y부터 같은 x 띠의 다음 라벨
y까지를 범위로 삼는다. **표 밖의 공통 섹션(「지원자격」)은 살린다** — 안 살리면 자격요건이
통째로 사라진다. 명세는 `step3.md` 3-B′.

**직무명을 코드에 박지 않는다.** 런타임 인자이므로 직군 무관 일반화를 깨지 않는다.

## LLM 사용 범위

- **공고 헤더 역할 분류** (텍스트만, 공고당 1회) — 이미지는 안 보낸다
- **조건 갈래 분류** (텍스트만, 공고당 1회) — 조건 하나가 이력서에서 **어떻게 확인되는가**를
  `term`/`binary`/`graded`로 받는다 (`rubric/branch.py`). 이미지도 좌표도 안 보낸다.
  **못 부르면 옛 글자 모양 규칙으로 떨어진다** — 이 판정에는 고를 수 있는 기본값이 있다
- **심사위원 채점** (루브릭이 판단 범위를 좁힌 상태에서만)
- 그 외 점수 계산에는 관여하지 않는다.
- 파싱 검증은 **LLM이 아니라 코드**로 한다. 기본 경로에서는 조건이 **OCR이 읽은 줄에서만**
  나오므로 검증이 따로 필요 없다. **VLM 폴백을 탄 경우에만** 추출값이 OCR 줄에 실재하는지
  대조하고, 매칭 실패한 조건은 좌표가 없어 **G4가 차단**한다.
  (LLM이 LLM을 검증하면 같은 실수를 두 번 한다.)
- **사람인 API의 조건성 필드는 읽지 않는다.** `experience-level`·`required-education-level`·
  `keyword`·`salary`·`job-code`는 **요구조건 텍스트 그 자체**라, 대조에만 쓰더라도 그 텍스트가
  결과에 영향을 준 것이 된다 — 과제 CRITICAL(원문 복붙 금지) 위반 소지. **`PostingMeta`에
  필드 자체를 만들지 않는다.** 담지 않으면 실수로 쓸 수도 없다. `docs/SARAMIN_API.md` §3.
  - **잃는 것**: 독립 대조군이 사라진다. 파싱 검증이 OCR 경로 안에서만 이뤄지므로
    **원본 이미지가 잘못됐을 때 잡을 자동 수단이 없다.** 남은 방어는 승인 게이트뿐이다.

## API의 역할 — 본문 파이프가 아니라 대조군

`docs/IMAGE_ACQUISITION.md` §3.5가 정본. **API는 데모·프로덕션 두 경로에 다 남는다.**
본문을 나르는 일만 데모 전용이다.

| 역할 | 쓰는 필드 | 하는 일 |
|---|---|---|
| ① 동일성 확인 | `company` · `position.title` · `posting-date` | 고객사가 보낸 게 실제 게시된 그 회사 공고인지 |
| ② **상태·수정 감시** | `active` · `expiration-date` · `modification-timestamp` | 마감 공고 채점 차단 · **공고 수정 시 승인 무효화** |
| ~~③ 파싱 교차검증~~ | — | **잘라냈다.** 쓰려던 필드가 요구조건 텍스트다 → `docs/SARAMIN_API.md` §3 |

**②가 승인 게이트와 직결된다.** 승인은 특정 revision에 대한 것이므로 공고가 수정되면
낡는다. `RubricProposal.posting_revision`에 `modification-timestamp`를 저장하고,
`score()`가 실행 시점에 재조회해 다르면 `ApprovalStale`을 던진다 (검산 G7).
